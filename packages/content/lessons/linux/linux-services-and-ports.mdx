Every service listening on a port is a way into the machine. Most images
ship at least one that has no business running. The skill is finding all of
them quickly, and then being disciplined about which ones you are allowed to
touch.

## Inventory first

```
sudo ss -tulpn
```

Read the flags as a sentence: TCP, UDP, listening, numeric, with process.
The `sudo` matters — without it you still see the ports, but the process
column comes back empty, and a port with no owner tells you very little.

The output gives you the port, the address it is bound to, and the program
holding it. An address of `0.0.0.0` or `[::]` means it is listening on every
interface — reachable from the network. `127.0.0.1` means local only, which
is a meaningfully smaller problem.

To see what systemd is managing:

```
systemctl list-units --type=service --state=running
```

## The usual suspects

These appear repeatedly on vulnerable images because they are legacy,
plaintext, or simply unnecessary:

- **telnet / telnetd** — plaintext remote login. There is no configuration
  that makes this acceptable; SSH replaces it.
- **vsftpd / FTP** — plaintext file transfer, and often configured to allow
  anonymous access.
- **rsh / rlogin** — older than telnet and worse.
- **Samba** — legitimate on file servers, unnecessary attack surface
  elsewhere.
- **Apache / nginx** — fine if the image is a web server, otherwise a full
  web server nobody asked for.

To stop one properly:

```
sudo systemctl disable --now telnet
```

`disable` stops it coming back at boot. `--now` stops it running this
second. Do one without the other and you have half-fixed it — which usually
scores nothing.

If the service should not exist at all, remove the package:

```
sudo apt purge telnetd
```

## The rule that costs the most points

**Read the README before you disable anything.**

Images routinely require a service that looks like an obvious problem. An
FTP server, a web server, even a database — if the README says it is part of
the scenario, stopping it is a **penalty**. Not a missed point, an actual
deduction, and often a large one because the scoring engine treats it as
breaking the machine's purpose.

A required service is not exempt from hardening. It is exempt from being
turned off. You still tighten its configuration, still remove anonymous
access, still restrict it to the interfaces it needs. The work changes shape,
it does not disappear.

Before you touch any service, ask: does the README name it? If yes, harden.
If no, disable. If you are unsure, re-read the README rather than guessing —
the penalty for a wrong guess is bigger than the point for a right one.
