Removing a user from the `sudo` group feels like you have handled privilege
escalation. Often you have not, because sudo takes its rules from more than
one place and only one of them is a group.

## Who currently has sudo

Group membership is the common path:

```
getent group sudo
```

That prints the sudo group and its members. To remove someone:

```
sudo deluser baduser sudo
```

Note what that does and does not do — it removes the user from the group,
not from the machine. If the README also says the account is unauthorized,
you still have to remove the account itself.

## The file that outranks the group

`/etc/sudoers` can grant privileges directly, without any group involved. So
can any file in `/etc/sudoers.d/`, because the main file includes that
directory. A single dropped-in file is enough:

```
sudo grep -r NOPASSWD /etc/sudoers /etc/sudoers.d/
```

`NOPASSWD` means sudo without a password prompt. On a hardened image there
is normally no reason for it to exist. Read what you find before deleting —
some images ship a legitimate rule the README depends on.

## Editing safely

Always:

```
sudo visudo
```

To edit a drop-in file specifically:

```
sudo visudo -f /etc/sudoers.d/somefile
```

`visudo` parses the file before it saves. If you introduce a syntax error it
refuses to write and tells you the line. Editing `/etc/sudoers` with a plain
editor and saving a typo means the next `sudo` fails, and with no root shell
already open there is no way back.

## What a good rule looks like

The default Ubuntu line is:

```
%sudo   ALL=(ALL:ALL) ALL
```

That grants the `sudo` group full privileges, with a password prompt. Rules
that deviate from this shape deserve a second look — particularly ones
naming an individual user, ones ending in `NOPASSWD: ALL`, and ones granting
a specific binary that can spawn a shell.
