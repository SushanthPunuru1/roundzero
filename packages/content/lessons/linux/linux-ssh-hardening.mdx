SSH is usually required to stay running, which makes it the one service
where a careless edit costs you twice: the scored item stays open, and you
lose your own access to the machine. The order of operations here matters
more than on any other item.

## The settings that get scored

In `/etc/ssh/sshd_config`:

```
PermitRootLogin no
PermitEmptyPasswords no
MaxAuthTries 3
X11Forwarding no
```

`PermitRootLogin no` is nearly always correct — administrators should log in
as themselves and escalate with sudo, which leaves an audit trail that
direct root login does not.

`PasswordAuthentication` is the one to read carefully. It is **not**
automatically "no". If the README says the team logs in with passwords,
setting it to `no` locks everyone out and costs points. Follow the README,
not habit.

## The drop-in trap

This is the single most common way to get SSH wrong on a modern image.

Ubuntu 22 and 24 ship a directory of include files:

```
/etc/ssh/sshd_config.d/
```

The main config includes it, typically at the very top — and in SSH's config
model **the first occurrence of a setting wins**. So a value in
`50-cloud-init.conf` beats the same value further down in `sshd_config`. You
edit the main file, restart cleanly, and the setting has not changed.

Always confirm against the merged configuration:

```
sudo sshd -T | grep -i permitrootlogin
```

`sshd -T` prints what sshd will actually use, after every include is
resolved. If the file says one thing and `sshd -T` says another, the drop-in
is the file you need to fix.

## Applying changes without locking yourself out

Test, then restart. Never the other way around:

```
sudo sshd -t && sudo systemctl restart ssh
```

`sshd -t` parses the config and reports syntax errors. The `&&` means the
restart only happens if the test passed. Get in the habit of typing both
halves together — a broken config plus a restart is how a remote box becomes
unreachable.

If you are working over SSH, keep your current session open while you test
the change in a second connection. Your existing session survives a restart;
a new one proves the config still lets you in.
